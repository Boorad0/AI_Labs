# ЛР 3

**Цель работы**
Цель работы — научиться проектировать, тестировать и документировать промпты и системные инструкции для решения прикладных задач с помощью LLM.
В ходе работы необходимо:
•	разобрать структуру качественной инструкции для LLM;
•	научиться отделять системную инструкцию от пользовательского запроса;
•	исследовать различия между простым, структурированным и пример-ориентированным промптом;
•	освоить подходы zero-shot и few-shot;
•	научиться задавать ограничения и требуемый формат ответа;
•	сформировать набор тестовых запросов и сравнивать версии промпта на одном и том же наборе данных;
•	научиться версионировать промпты и фиксировать причины изменений;
•	выявлять неясные, противоречивые и небезопасные инструкции;
•	сформировать рабочий промпт для бизнес- или ИБ-сценария и обосновать его структуру.

**Описание моделей**

Qwen3.5 — это семейство больших языковых моделей от компании Alibaba Cloud, выпущенное в феврале 2026 года. Оно включает несколько вариантов с разным количеством параметров (от 0.8B до 397B), что позволяет подобрать решение под конкретные задачи: от запуска на ноутбуке до работы с огромными массивами данных в облаке.

**Способ доступа**

LM Studio развернута на домашнем ПК. Запросы к модели отправляются с ноутбука. Для установления соединения между ноутбуком и домашним ПК на обоих устройствах запущен Radmin VPN, обеспечивающий их взаимодействие через виртуальную частную сеть.

**Запуск**
Установить зависимости:
```
pip install -r requirements.txt
```
Создать .env на основе примера и указать реальные значения:
```
cp .env.example .env
```
Запустить LM Studio, загрузить нужную модель и включить локальный сервер (обычно на порту 1234). Проверить, что нужная модель реально загружена:
```
curl http://localhost:1234/v1/models
```
Запуск кода:
```
python main.py
```
**Переменные окружения**
```
API_TOKEN=      # Токен LM_Studio
LMM_BASE_URL=   # адрес сервера, по умолчанию http://localhost:1234/v1
LMM_MODEL_1=    # точное имя модели 1, загруженной в LM Studio
```
**Результаты**
в results.json

Вывод

Наибольший эффект дал переход от v1 к v2 — прирост с 53 до 93 баллов. Причина в том, что v1 вообще не задавал модели ни роль, ни формат, ни ограничения - модель писала развёрнутое эссе с выводами вроде «подтверждённая кибератака» без единого упоминания, каких данных не хватает. Простое введение структуры решило сразу две проблемы: сделало формат воспроизводимым и заставило модель явно останавливаться на недостатке данных вместо того, чтобы додумывать факты.

Переход от v2 к v3 дал куда более скромный прирост, но решал качественно другую задачу, которую v2 не закрывал: v2 был устойчив по содержанию, но оставался текстом, непригодным для программной обработки. v3 добавил few-shot-примеры и строгий JSON-формат - в результате ответы стали валидным JSON, а устойчивость к попытке подмены правил не пострадала, хотя формат был куда более хрупким. То есть v3 не столько повысил качество ответа, сколько перевёл промпт из категории «текст для чтения» в категорию «интерфейс для программы».

Если тестируется восприятие ответа человеком - решающий эффект даёт структура (v2). Если ответ должен потребляться программой - решающий эффект даёт few-shot + строгий формат вывода (v3).

**Контрольные вопросы**

1. Что такое промпт в контексте прикладной LLM-системы?
Промпт - это не разовая реплика в чате, а компонент программной системы: набор инструкций и данных, передаваемых модели для получения нужного результата. Как и любой другой компонент программы, он должен быть воспроизводимым, тестируемым, версионируемым и связанным с конкретными критериями качества, а не «удачной формулировкой», найденной один раз.

2. Чем system prompt отличается от user prompt?
System prompt содержит постоянные правила поведения приложения - роль модели, ограничения, формат ответа — и задаётся разработчиком системы. User prompt содержит переменные данные конкретного запроса. Разделение важно потому, что пользователь не должен иметь возможности обычным текстом запроса переопределить постоянные требования приложения.

3. Для чего в инструкции используются Role, Task, Context, Constraints и Output Format?

Role задаёт точку зрения и уровень компетенции, с которой модель должна рассуждать.
Task формулирует конкретное действие, а не общее «помоги».
Context передаёт исходные данные, на которые модель должна опираться, а не придумывать свои.
Constraints задают, чего делать нельзя и что делать при неопределённости.
Output Format делает ответ предсказуемым и пригодным для дальнейшей обработки..

4. Чем zero-shot отличается от few-shot prompting?
Zero-shot - модель получает только инструкцию, без примеров ответа. Few-shot - в промпт добавляются 2–3 примера «вход - ожидаемый выход», которые показывают модели не только что делать, но и как именно должен выглядеть результат в пограничных случаях. Few-shot дороже по токенам, но полезен, когда формат или границы категорий сложно описать одними словами - именно поэтому я использовал его для перехода на строгий JSON.

5. В каких случаях few-shot-примеры могут ухудшить результат?
Если примеры нерепрезентативны или содержат систематическую ошибку — модель добросовестно перенесёт эту ошибку на новые случаи, потому что воспринимает примеры как образец, а не как иллюстрацию. Также вред возможен, если примеры выбраны однобоко - тогда модель начинает завышать риск даже для нейтральных событий, либо если примеров слишком много и они «размывают» основную инструкцию, конкурируя с ней за внимание модели.

6. Почему инструкция «верни JSON» не гарантирует синтаксически корректный JSON?
Потому что модель генерирует текст токен за токеном на основе вероятностей, а не по формальной грамматике - текстовая просьба «верни JSON» это лишь подсказка о стиле, а не техническое ограничение вывода. Модель может обернуть ответ в json, добавить пояснение до или после, забыть закрывающую скобку в длинном списке. 

7. Почему промпт нельзя считать средством разграничения доступа?
Промпт управляет поведением модели через естественно-языковую инструкцию, но не является техническим барьером - модель не может на 100% гарантированно отличить «системную инструкцию» от искусно замаскированного пользовательского текста, поэтому prompt injection в принципе возможен. Реальное разграничение доступа должно обеспечиваться на уровне архитектуры системы - правами API-ключа, валидацией на бэкенде, авторизацией запроса, а не текстом промпта.

8. Что такое критерий отказа и зачем он нужен?
Критерий отказа - это явно прописанное в промпте правило поведения при неопределённости: что модель должна делать, если данных недостаточно.

9. Почему промпты следует версионировать и тестировать на фиксированном наборе входов?
Без версионирования невозможно объективно сказать, что именно изменение промпта дало эффект. Фиксированный набор тестов превращает промпт-инжиниринг из субъективного «мне кажется, стало лучше» в измеримый процесс.

10. Какие признаки указывают, что проблема находится не в промпте, а в данных, модели или архитектуре системы?

Проблема воспроизводится даже на хорошо структурированном промпте и не устраняется дальнейшим уточнением инструкций - например, если модель систематически путает базовые факты независимо от формулировки задачи, дело в возможностях модели.
Ошибка связана с отсутствием или неполнотой входных данных, а не с формулировкой задачи - тогда решение не в промпте, а в том, откуда система берёт контекст.
Модель корректно выполняет задачу, но результат всё равно ломает систему - например, валидный JSON приходит, но бэкенд падает при его обработке - это архитектурная проблема, не промпт.
Проблема не устраняется даже few-shot-примерами и явными критериями отказа и повторяется на разных версиях промпта - сигнал, что причина не в формулировке инструкции, а в структурных ограничениях модели или системы.
